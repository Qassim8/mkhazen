## 2. ما تغطيه الاختبارات

### اختبارات الوحدة (`tests/unit/`)
- **`session-token.test.ts` (8):** توكن صالح/منتهي/مفقود/متلاعب؛ مفتاح مختلف وخوارزمية `none` مرفوضان؛ توكنات ما قبل التحديث تُعامل كمنتهية؛ الحد الأقصى المطلق؛ التجديد بعد 15 دقيقة مع الحفاظ على البصمة؛ بصمة كلمة السر تتغير ولا تكشف الهاش.
- **`api-client.test.ts` (14):** رفض 17 حمولة SSRF/traversal؛ تحويل 401 لصفحة انتهاء الجلسة مع `next`؛ 403 لا يحوّل؛ انقطاع الشبكة = `status 0`؛ نقرتان = طلب واحد؛ same-origin/no-store؛ مسار الخادم لا يصل له مسار غير آمن؛ `safeReturnPath` (12 حالة open redirect).
- **`domain.test.ts` (16):** صلاحيات الأدوار والصفحات ومنع حلقات التحويل؛ تنظيف البحث من حقن الفلتر؛ التحقق من أسعار السلة (مجموع مرفوع، منتج غير نشط، هدية بصفر)؛ توزيع تكلفة الشراء (المثال الموثق 65 للقطعة، الخصم، عدم السالب)؛ العملات؛ بصمة منع التكرار؛ حد المحاولات؛ **جدول مسارات الـ API كامل** (اكتشف 3 مسارات ناقصة)؛ **لا يوجد `"use server"`**؛ كلمة السر المؤقتة.

> **تحديث المرحلة الثانية:** اختبارات SQL صارت تعمل على **المخطط الحي المصدَّر** (`live_public_schema.sql`) لا مخطط تخميني، والأعداد المحدّثة في القسم 8. الوصف أدناه للمرحلة الأولى.

### اختبارات SQL (`database/tests/`، كل ملف على أعمدة `text` و`enum`)
- **`purchases.db.test.ts` (19):** استلام صحيح مطابق لحساب التطبيق (كرتونة 10 قطع + توصيل + خصم)؛ الاستلام المكرر مرفوض بلا زيادة مخزون؛ **فشل بند في المنتصف يلغي كل شيء** (لا مخزون جزئي، لا حركات، لا قيد، الحالة كما هي)؛ متوسط مرجّح مع رصيد قائم؛ رفض المسودة/الملغي/غير المخوّل؛ الدفعة + القيد معًا؛ منع تجاوز المتبقي؛ منع الدفع برصيد دولار غير كافٍ (رصيد الجنيه لا يُحتسب)؛ رفض المبالغ والطرق غير الصالحة؛ الدفع بعد الاستلام؛ إعادة تشغيل الـ migration، التحقق، الرجوع دون مساس بالبيانات.
- **`ledger.db.test.ts` (1):** 400 قيد عشوائي على سنتين + حدود منتصف الليل والسنة بتوقيت السودان → الأرصدة والأداء الشهري من المجاميع **مطابقة تمامًا** للحساب من القيود الخام.
- **`audit-sql.db.test.ts` (4):** كل استعلامات ملفات المراجعة الثلاثة تُنفذ وهي قراءة فقط؛ فحص تطابق المخزون لا يُظهر فرقًا بعد الاستلام الذرّي ويكشف أي تعديل يدوي للرصيد.

### اختبارات التكامل (`tests/e2e/api-auth.e2e.test.ts`، 18)
تشغّل نسخة الإنتاج الحقيقية (`next start`) بالـ proxy والـ routes والكوكيز:
1. API بلا جلسة → 401 `UNAUTHENTICATED` بالعربي.
2. توكن متلاعب/منتهي/قديم → 401 `SESSION_EXPIRED` + مسح الكوكي.
3. كلمة سر تغيّرت بعد الجلسة / حساب معطل → 401 من الـ route.
4. كاشير على المحاسبة/الموظفين/المشتريات/التقارير → 403 `FORBIDDEN`؛ خياط على فاتورة → 403.
5. طلب تعديل من Origin آخر → 403 `CSRF_REJECTED`.
6. الصفحات: بلا جلسة → `/`؛ منتهية → `/session-expired?next=/dashboard/pos?tab=1`؛ صلاحية ناقصة → الصفحة الرئيسية للدور.
7. صفحة انتهاء الجلسة بالعربي، و`next` خارجي لا يصبح رابطًا.
8. Security headers و`no-store` للـ API وإخفاء `X-Powered-By`.
9. الدخول: كلمة سر غلط → 401 عام؛ الحساب المعطل يُكشف فقط بعد كلمة السر الصحيحة؛ النجاح → كوكي `HttpOnly; SameSite=lax; Max-Age=43200`.
10. 11 محاولة دخول فاشلة → 429.
11. طلب إعادة التعيين: نفس الرد للموجود وغير الموجود.
12. البيع: بيانات/كمية سالبة → 422؛ مجموع مرفوع لتمرير خصم → 409 مع الأسعار الحالية ودون استدعاء دالة البيع؛ **نفس `Idempotency-Key` مرتين = بيع واحد ونفس الفاتورة (`replayed`)**، نفس المفتاح ببيانات أخرى → 422؛ سعر صرف تغيّر → 409؛ رفض القاعدة (نفاد المخزون) يصل بالعربي ويحرر المفتاح؛ خطأ قاعدة داخلي لا يتسرب نصه.
13. كل طلبات قاعدة البيانات وصلت للخادم الوهمي فقط.

### تحسينات منفذة
- **صفحة المحاسبة:** من تنزيل كل القيود مرتين (⌈N/1000⌉ × 2 طلب متتالي) إلى طلب واحد يعيد صفوفًا مجمّعة (حسابين × عملة × نوع × شهر) — عدد الصفوف ثابت تقريبًا مهما كبر الدفتر (يتطلب migration 02).
- **جلب بيانات الصفحات:** إزالة طلب HTTP الداخلي لكل `serverFetch` من الخادم (رحلة شبكة + invocation إضافية على Vercel) → استدعاء داخلي مباشر.

### غير منفذ (موثق)
- قائمة المبيعات تحمّل كل المبيعات المكتملة (P2-3)، ولوحة التحكم والتقارير تحسب في JS (P2-4) — تحتاج قياسًا على بيانات حقيقية ثم ترقيمًا في قاعدة البيانات.

## 6. قائمة اختبار يدوي على staging (مطلوبة قبل الإنتاج)

**الكاشير:** بيع عادي ✔ · نفس المنتج مدفوع + هدية في فاتورة واحدة (الإجمالي لا يشمل الهدية، المخزون ينقص بالكميتين، قيد هدية بلا إيراد) ✔ · عدة منتجات ومتغيرات ✔ · خصم 50% بالضبط ✔ و50.01% ✘ · دفع مختلط مطابق ✔ وغير مطابق ✘ · بيع آخر قطعة من جهازين في نفس اللحظة (واحد ينجح) ✔ · نقر مزدوج سريع على «إتمام» (فاتورة واحدة) ✔ · DevTools → Offline بعد الضغط ثم Online وإعادة المحاولة (فاتورة واحدة + رسالة «تم تأكيد العملية السابقة») ✔ · إعادة تحميل بعد النجاح (لا تكرار) ✔ · طباعة الإيصال ✔.
**الجلسة:** على staging ضع `SESSION_IDLE_HOURS=0.02` (≈ دقيقة)، افتح الكاشير وأضف للسلة، انتظر، اضغط «إتمام» → صفحة «انتهت جلستك» → دخول → العودة للكاشير والسلة مستعادة ولم يتم أي بيع تلقائي ✔ · تغيير كلمة السر من جهاز → الجهاز الآخر يُطلب منه الدخول ✔ · تعطيل موظف → يخرج خلال ≤ 30 ثانية ✔.
**المشتريات:** إنشاء مسودة ← اعتماد (المالك) ← استلام (المخزون × معامل التحويل، المتوسط، قيد المخزون/الموردين) ← دفعة جزئية ← دفعة تتجاوز المتبقي ✘ ← دفعة برصيد غير كافٍ ✘ · استلام نفس الطلب من تبويبين معًا (واحد فقط) ✔ · شراء مباشر ✔.
**التفصيل:** إنشاء بعربون ← UNDER_TAILORING (خصم القماش مرة واحدة حتى مع الضغط مرتين) ← READY ← تسليم وتحصيل الباقي ✔ · إلغاء بعد خصم القماش (راجع القرار D12) · استرداد عربون جزئي ثم استرداد أكبر من المتبقي ✘ · دفع خياط ✔.
**المحاسبة:** تحويل عملة بربح/خسارة صرف ✔ · مصروف برصيد غير كافٍ ✘ · مطابقة أرقام لوحة المحاسبة قبل/بعد migration 02 (يجب أن تتطابق) ✔.
**بعد كل ذلك:** شغّل `database/audit/03_data_integrity_checks.sql` (يجب ألا يرجع صفوفًا لعمليات الاختبار).

## 7. الحكم النهائي

> **محدَّث في القسم 8** (المرحلة الثانية). خطوات «ما يجب فعله» أدناه استُبدلت بـ [release-plan.md](release-plan.md).

### **جاهز للاختبار النهائي قبل الإنتاج** — وليس جاهزًا للإنتاج بعد.

**الأساس:**
- كل مشكلات P0 وP1 القابلة للإصلاح داخل المستودع أُصلحت واختُبرت (80 اختبارًا آليًا ناجحًا + بناء إنتاج ناجح + 0 ثغرات في اعتماديات الإنتاج + 0 Server Actions مكشوفة + 0 أسرار في حزمة المتصفح).
- **لكن** منطق البيع والتفصيل والتسويات المالي يعيش في دوال قاعدة بيانات غير موجودة في المستودع، وحالة RLS/صلاحيات anon على القاعدة الحقيقية غير معروفة، والـ migrations الجديدة لم تُطبَّق على قاعدة Supabase حقيقية بعد. لا يمكن ضمان سلامة المال والمخزون قبل هذه الخطوات.

### ما يجب على صاحب النظام فعله قبل اعتماد النسخة (بالترتيب)

1. **نسخة احتياطية** من قاعدة الإنتاج والتأكد من خطة النسخ في Supabase (يومية/PITR)، وإنشاء مشروع **staging** من النسخة.
2. على staging: تطبيق `database/migrations/20261009_01_…sql` ثم `…_02_…sql` من SQL Editor، وتشغيل `20261009_01_…verify.sql` (كل الصفوف «سليم»).
3. تشغيل `database/audit/01_security_audit.sql` على **الإنتاج** (قراءة فقط) وإصلاح أي نتيجة في الاستعلامات 1–5 (جداول بلا RLS، صلاحيات anon، دوال SECURITY DEFINER قابلة للتنفيذ).
4. تشغيل `database/audit/02_dump_app_functions.sql` وحفظ الناتج في `database/snapshot/functions/` ومراجعة الدوال بأسئلة القسم 6 من التقرير (خاصة `complete_sales_checkout` و`update_tailoring_status`).
5. تشغيل `database/audit/03_data_integrity_checks.sql` و`…verify.sql` على الإنتاج: معالجة أي أمر شراء معلّق أو مبيعات مكررة من المشكلات القديمة **يدويًا وبقرار محاسبي**.
6. نشر الفرع على Vercel **Preview** مربوطًا بـ staging، وتنفيذ قائمة الاختبار اليدوي (القسم 6) كاملة.
7. اتخاذ القرارات D1–D12 (على الأقل D5 المرتجعات وD6 الأرصدة الافتتاحية) قبل التشغيل الفعلي.
8. على الإنتاج: تطبيق الـ migrations (بعد نجاح staging) **ثم** نشر التطبيق؛ إبلاغ الموظفين أن الكل سيعيد تسجيل الدخول مرة؛ إعادة تعيين كلمات سر الحسابات التي لم تغيّر كلمة سرها الافتراضية القديمة.
